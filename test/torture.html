颠倒黑白 缺陷复现 · torture

单个页面，分区复现可视化缺陷。深色底 #0d0d1a。每节标题写明「在考什么」，页尾有对照清单。

§1 反向滤镜的还原度 — 考 Filter 模式的反向滤镜能否精确抵消

扩展给整页加了一层滤镜，再给图片（<img> / canvas / picture）套上同一个滤镜，想把自己加的那层抵消掉。反向滤镜与整页滤镜是同一个值，所以它必须对合：invert(100%) 与 hue-rotate(180deg) 各自对合，且作用顺序可交换，组合起来也就是对合的（F(F(x)) = x）。

但存在先天极限：中间结果一旦超出色域，会被浏览器钳制到有效范围内，而钳制不可逆，所以全饱和原色（纯红 / 纯绿 / 纯蓝）仍无法精确还原；灰阶与低饱和色不受影响，偏差为 0。

下面的图片每张都标了「原本长什么样」，请对照着肉眼判断有没有被改坏——现在预期是基本还原成原样；再往下的「数值化往返测试」用 canvas 把偏差算成具体数字。

小图标 32×32，原本：浅底上一个深灰圆点。扩展的图片分类逻辑有 naturalWidth < 100 && naturalHeight < 100 就跳过的门槛，看它会不会绕过这张小图、但仍然照套反向滤镜。

数值化往返测试 — canvas 实测 F(F(x))，看反向滤镜到底抵消了多少

做法：给每个测试色造一个 1×1 的 canvas 填上该色，把 LON_FILTER 连续套两次（第一次的结果画到第二个 canvas，再套一次同一个 filter）得到 F(F(x))，读回像素与原色逐通道比较。理想情况下图片应该原样不动，所以「期望值」这一列就是原色本身。

LON_FILTER = invert(100%) hue-rotate(180deg) —— 这个值必须和 content.js 里的 INVERT_FILTER 保持一致，否则测出来的是另一回事。

  • §1（Filter 模式）· 数值化往返测试：扩展给图片套的反向滤镜用的是同一个滤波器，所以它必须对合——invert(100%) 与 hue-rotate(180deg) 各自对合且可交换，组合起来也是对合的。
					灰阶那几行偏差应当是 0 或 ±1；红 / 绿等全饱和原色仍有偏差，属已知极限（超色域被钳制、钳制不可逆）。
					若表格显示「本浏览器不支持 canvas filter」，说明浏览器没跑测试，不代表没有偏差，请换 Chrome / Edge。
    • 
				
  • §1 图片（肉眼）：三张 data-URI 图各配了「原本长什么样」的说明，对照着看有没有被改坏——现在预期是基本还原成原样。若明显发闷、发黄、深底变浅底，说明反向滤镜没抵消干净。
    • 
				
  • §1 小图标：32×32 因 < 100px 门槛会被跳过分类，但仍会被 counter-filter 命中 —— 说明尺寸门槛没有绕过滤镜本身。
    • 
				
  • §2（Remap 模式）：鲜艳色块保留原色相、收成同色相的浅色块（例如 #2962ff → 浅蓝、#9400d3 → 浅紫），深色按钮变成浅底 + 深色字；中性深色（近黑、slate-900 这类）落到奶油底 #fdf6e3。
					若某块颜色没变（如 #00c853、#00bcd4），说明重映射的亮度阈值把它漏掉了 —— 部分色块处理、部分不处理，页面会花。
    • 
				
  • §3：声明了 color-scheme: dark，滚动条初始应为深色。
					翻浅后滚动条仍是深色 → 扩展没处理 color-scheme，视觉不协调。
    • 
				
  • §4：点击后应能持续出帧。
					若 rAF 帧率明显掉到个位数、每轮耗时飙到几十上百 ms，说明 MutationObserver 对大批 class 变动 + 自写 inline style 的处理造成了卡顿。
    • 
				
  • §5：渐变文字应保留色相、压深到读得清。变透明/消失 = 失败。
    • 
				
  • §6：::before 圆点、::after 叠加里用的是伪元素颜色，逐元素重映射拿不到。保持深色、和浅色页面不协调 = 已知缺陷。
    • 
				
  • §7：渐变背景应被替换为纯色。若仍是渐变、或变成难看的整块色，说明渐变处理不完整。
